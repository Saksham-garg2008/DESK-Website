DESK / CONTRIBUTE / ALPHA EDITION

Good software
is built together.

DESK is an open-source desktop AI project under active development. Contributions can improve its code, documentation, reliability, platform behaviour, and overall usability. Start small, understand the existing implementation, and make every change count.

01 / WHERE TO HELP

Useful contributions take many forms.

You do not need to start with a major feature. Clear bug reports, accurate documentation, and focused fixes can all make the project better.

01 / RELIABILITY

Fix a problem

Reproduce a bug, identify its cause, and submit a focused fix with a clear explanation of the behaviour before and after.

02 / DOCUMENTATION

Make things clearer

Improve setup instructions, explain confusing workflows, correct outdated information, or make technical documentation easier to follow.

03 / TESTING

Check real behaviour

Test supported workflows, report reproducible failures, and identify differences across operating systems or configurations.

04 / MAINTAINABILITY

Improve the code

Make existing code easier to understand, remove unnecessary complexity, and preserve clear boundaries between components.

05 / COMPATIBILITY

Consider different systems

Help identify platform-specific issues and make installation or supported workflows more dependable across environments.

06 / USER EXPERIENCE

Improve everyday use

Suggest or implement focused improvements to interface clarity, accessibility, feedback, and the way users understand an action's result.

02 / CONTRIBUTION WORKFLOW

Make changes that are easy to review.

A little preparation makes contributions safer, easier to understand, and less likely to duplicate existing work.

01

Understand first

Read the README and relevant code. Search existing issues and discussions to see whether the problem or proposed change has already been raised.

02

Keep it focused

Make one clearly defined change at a time. Avoid unrelated refactoring, unnecessary dependencies, and changes that make the project's behaviour harder to predict.

03

Test and explain

Test the affected workflow where possible. Describe what changed, why it changed, the environment used, and any limitations or cases you could not test.

BEFORE CODING

Discuss the change

For a substantial feature or architectural change, consider opening an issue or discussion first. Explain the problem you want to solve and the approach you have in mind before investing time in a large implementation.

Open the issue tracker ↗
WHEN SUBMITTING

Give context

A useful pull request explains the problem, the chosen solution, the files or components affected, and the tests performed. Include screenshots for visual changes when appropriate, and mention any known limitations.

Review repository guidance ↗

04 / PROJECT PRINCIPLES

Improve DESK without losing its focus.

A

LIGHTWEIGHT BY DESIGN

Keep dependencies purposeful.

Consider installation complexity, memory use, and compatibility before adding dependencies. Prefer straightforward solutions when they meet the requirement without unnecessary overhead.

⌘
B

PREDICTABLE BEHAVIOUR

Respect boundaries.

Changes involving desktop actions, files, or external communication should make the supported behaviour and its limitations clear. Do not broaden permissions or imply unrestricted access without a deliberate, reviewed design.

◇
C

CROSS-PLATFORM CARE

Make assumptions explicit.

Avoid hardcoded machine-specific paths and assumptions about installed applications. Where possible, use platform-aware behaviour and document any remaining requirements.

⌘
D

DESKTOP + ANDROID

Keep integration changes coordinated.

If a change affects the Android Companion, explain whether corresponding desktop changes are needed. Test the end-to-end workflow when possible and document any protocol or behaviour changes.
